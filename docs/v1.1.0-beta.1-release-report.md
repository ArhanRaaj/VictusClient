# VictusClient v1.1.0-beta.1 — Launch Regression Fix & Release Report

## 1. Summary

**Symptom:** clicking **Launch Minecraft** made the launcher hang ("Not Responding"); Minecraft
never started and the operation could not be cancelled.

**Root cause:** a synchronous `execSync` call to `curl.exe` was added to the *per-file* download
path. Every client jar, library, native and asset download blocked the Electron **main process**
event loop for the full network duration, which froze the entire application. With a cold cache
that is thousands of blocking calls, so the freeze was effectively unbounded.

**Fix:** downloads are fully async again, the launch pipeline can be cancelled at any point, a
failed spawn no longer leaves the launcher stuck, and the whole pipeline is platform-correct.

---

## 2. Root cause (evidence, not assumption)

### The regression

| | |
|---|---|
| Commit | `a407d52` — *"fix(launcher): implement resumable chunked downloads with curl accelerator and byte verification to prevent socket drop BAD_DECRYPT errors"* |
| File | [`electron/core/MinecraftLauncher.ts`](../electron/core/MinecraftLauncher.ts) |
| Code | `execSync("C:\\Windows\\System32\\curl.exe" … -o <file> <url>, { timeout: 120000 })` inside `downloadFile()` |

`execSync` blocks the Node/Electron event loop until the child process exits. Because
`downloadFile()` runs once per missing file (client jar, every library, every native, every asset
object) the main process could not service IPC, timers or window messages for the entire
download phase → the OS marks the window **Not Responding**, and Minecraft never gets spawned.

### Measured proof of the mechanism

A timer representing pending UI/IPC work, measured around a single blocking synchronous child
process of ~700 ms:

```
blocking op took:        778 ms
50ms timer fired after:  778 ms      <-- UI work delayed by the whole operation
```

Every millisecond of every download was spent with the main process blocked.

### Proof of the fix

`scripts/verify-launch-pipeline.js` downloads an 8 MB payload through the real `downloadFile()`
path while sampling event-loop lag:

```
PASS  download completes with the exact expected byte count — 8388608 / 8388608 bytes
PASS  main thread stays responsive during download (lag < 250ms) — max event-loop lag 0ms
PASS  no leftover .part file after a successful download
PASS  in-flight download aborts when cancellation is requested — outcome: LaunchCancelledError
PASS  cancelled preparation returns promptly instead of hanging — {"success":false,"error":"Launch cancelled"}
PASS  unknown version fails fast with an error message — 85ms
PASS  failure is reported to the UI as an error status
PASS  Java detection completes and never blocks indefinitely
```

### 2.2 Second root cause, found during live launch testing

The freeze fix made launches reach Java, which exposed two further defects.

**a) Native archives from every architecture were extracted into one directory.**

Minecraft metadata encodes the native target architecture in the *maven classifier* rather than
in `os.arch` rules — `26.3.json` contains 56 native entries with **zero** `os.arch` rules. The
first-pass selection accepted any `:natives-*` artifact whose (OS-only) rules passed, so for each
library the x64, `-x86` **and** `-arm64` archives were all downloaded, extracted and added to the
classpath. Because all three variants ship the *same* file names, the last one extracted won.

A live instance's `natives/` folder after a crash:

```
arm64  freetype.dll     arm64  lwjgl.dll        arm64  SDL3.dll
arm64  jemalloc.dll     arm64  lwjgl_opengl.dll arm64  shaderc.dll
arm64  OpenAL.dll       arm64  lwjgl_stb.dll    arm64  spirv-cross.dll
```

That folder is first on `java.library.path`, ahead of LWJGL's own arch-correct extraction in
`natives/3.4.3-snapshot/x64/`, so the JVM loaded **arm64** images on an x64 machine and died with
`0xC0000005` (Windows exit code `3221225477`) mid-render — no Java exception, no crash report.

The regression was introduced by the first pass of this very fix and is corrected by selecting
exactly one archive per library based on the **resolved JVM architecture** (a 32-bit JVM on 64-bit
Windows needs `natives-windows-x86`), derived from the classifier name rather than os rules.

**b) The launcher would launch with a Java runtime that is too old.**

`26.3.json` declares `"javaVersion": {"majorVersion": 25}`; the launcher silently fell back to the
newest installed runtime (Java 17) and the game died with
`UnsupportedClassVersionError: … class file version 69.0 … up to 61.0`. The runtime is now
resolved *before* libraries (its architecture is needed for native selection), a JVM older than
the declared requirement is rejected instead of used, and the missing runtime is provisioned
automatically through Adoptium (with progress) so the launch proceeds instead of failing.

`scripts/inspect-native-selection.js` is the diagnostic that pinpoints this class of bug:

```
$ node scripts/inspect-native-selection.js 26.3
Instance inst-1790668012549: 22 native file(s) in natives/
   ...
  ❌ WRONG ARCHITECTURE for a x86_64 JVM — this causes native crashes:
     - freetype.dll (arm64)
     - lwjgl.dll (arm64)
     - SDL3.dll (arm64)
     ...
```

## 3. What changed

### 3.1 The launch freeze (`electron/core/MinecraftLauncher.ts`)

* **Removed the `execSync` curl accelerator.** All downloads use the async streaming HTTP/HTTPS
  downloader with resume (`Range`), redirect handling, per-request timeouts, retry/backoff and
  byte-count verification. The unused `execSync` import is gone.
* **Second main-thread blocker removed.** `JavaManager.detectInstallations()` used `execSync`
  (`where java`, `java -version`, no timeout on `where`) plus a synchronous recursive directory
  scan — on the launch path. Java probing is now fully async (`execFile`), platform-aware, and
  cached for 60 s.
* **Cancellation.** `kill()` during preparation now aborts the pipeline at the next checkpoint
  (including mid-download) and reports a clean "cancelled" state instead of hanging.
* **Launch state can no longer wedge.** A `spawn` `'error'` (e.g. Java missing) previously left
  the instance stuck on *"Minecraft is running"* forever; it now clears the process, publishes an
  `error` progress status and emits the exit event so the UI returns to a usable state.
* **Double-launch guard.** An instance that is already preparing/running is rejected instead of
  spawning a second JVM and leaking the first handle.
* **Real process termination.** On Windows `kill()` now terminates the whole process tree
  (`taskkill /T /F`) instead of sending a `SIGTERM` that Minecraft ignores.
* **Accurate run/exit reporting.** "Minecraft is running" is emitted on the process `'spawn'`
  event (or first output) rather than blindly after `spawn()`; `close` and `error` are
  de-duplicated; a non-zero exit logs an explicit diagnostic.
* **Bounded logging.** Child stdout/stderr is line-split and flushed in batches (60 ms / 100
  lines, ≤ 8 KB per line) so a crash stacktrace cannot flood IPC and stall the renderer.
* **Natives directory is rebuilt per launch** so stale platform libraries from a previously
  launched version can never be loaded by the JVM.
* **PID-correct JVM flags.** `--enable-native-access=ALL-UNNAMED` only exists on Java 17+; it is
  now omitted on older runtimes (passing it made Java 8/11 refuse to start), and the required
  Java major now comes from the version manifest instead of being hardcoded to 21.
* **One arch-correct native per library** (see §2.2a) — the JVM architecture decides the
  classifier, other OS/arch archives are skipped entirely, and the natives directory is rebuilt
  on every launch so a previously polluted one self-heals.
* **Runtime requirement enforcement + provisioning** (see §2.2b) — the version's declared Java
  major is resolved before libraries; a runtime older than required is refused and the missing
  runtime is downloaded automatically.
* **Actionable crash reporting** — process exit codes are translated (Windows NTSTATUS values
  such as `3221225477` → ACCESS_VIOLATION with the likely cause), and an intentional stop is no
  longer reported as an unexpected crash.
* **Platform-correct GPU environment** — the GLX/PRIME offload variables are only set on Linux
  and `SHIM_MCCOMPAT` only on Windows, instead of all three on every platform.

### 3.2 Cross-platform launch correctness

The previous pipeline was hardcoded to Windows:

| | Before | Now |
|---|---|---|
| Rule evaluation | `rule.os.name === 'windows'` only | `win32→windows`, `darwin→osx`, `linux→linux`, plus `os.arch` / `os.version` / `features` rules |
| Natives | `classifiers['natives-windows']` only | legacy `natives-*` classifiers **and** 1.19+ native artifacts (`:natives-*`), resolved per platform, honoring `extract.exclude` |
| Native extraction | `.dll` only | `.dll` / `.dylib` / `.jnilib` / `.so` per platform |
| Classpath separator | hardcoded `;` | `path.delimiter` (`:` on macOS/Linux) |
| Loader JVM args | ignored | Fabric/Quilt profile `arguments.jvm` are applied |
| Java discovery | Windows paths + `where.exe` | Windows, macOS (`/Library/Java/JavaVirtualMachines`, Homebrew, SDKMAN) and Linux (`/usr/lib/jvm`, SDKMAN) |
| Adoptium download | `windows/x64` zip always | OS/arch-aware, `.zip` on Windows and `tar.gz` elsewhere |

### 3.3 Renderer (`src/context/LauncherContext.tsx`)

A failed or cancelled launch now surfaces a notification with the real error message instead of
failing silently. No other renderer behaviour was touched.

### 3.4 Release scripts (fixes required to produce trustworthy artifacts)

* `scripts/package-linux.js` — shelled out to `tar`, which under Git Bash resolves `C:\...` as a
  remote host and failed; now extracts with AdmZip. It also had the same download race as
  `package-mac.js` (resolved on `res.end` without awaiting the write stream), which produced a
  **truncated** Electron archive (no ZIP end-of-central-directory record). Both scripts now verify
  `content-length` **and** ZIP integrity and only then rename the file into the cache.
* `scripts/package-mac.js` / `package-linux.js` — Windows `stat()` cannot express the Unix
  executable bit, so the packaged macOS/Linux launchers were shipping non-executable. The
  executable bit is now written explicitly into the archive (verified below).
* `scripts/verify-launch-pipeline.js` (new), `scripts/verify-release-artifacts.js` (new),
  `scripts/stage-windows-installers.js` (new) plus `npm run verify:launch`, `verify:release`,
  `stage:windows`.
* `scripts/publish-beta.js` — added the requested installer names and the (previously missing)
  Linux archive to the uploaded asset list.

## 5. Not verified in this environment

* **Windows 7 x64/x86** and **Windows 11** — only the current Windows host was exercised; the
  Electron 33 runtime is the same, but the Windows 7 install path (and `taskkill`, `javaw.exe`
  resolution) was not executed on those OS versions.
* **macOS** artifacts were produced with architecture and permission bits verified, but they are
  **unsigned / not notarized** and were zipped on Windows (AdmZip duplicates framework symlinks).
  Regenerate the `.dmg`/signed bundle on macOS before publishing to end users.
* **Linux** ships as the project's existing portable zip. It is not an AppImage/deb (those targets
  in `package.json` require a Linux host or Docker). Electron's `chrome-sandbox` needs root
  ownership with mode 4755, which a ZIP cannot carry — users must either fix it up or launch with
  `--no-sandbox`.
* A **real end-to-end launch** was exercised on the Windows test host: the launcher spawned Java,
  resolved the runtime, loaded the LWJGL/SDL3/OpenAL natives, created the window and reached
  resource loading before hitting the two defects in §2.2 (wrong-architecture natives, then an
  out-of-date JVM). Both are fixed and covered by `verify:launch`, and both are diagnosed from
  real evidence rather than inference — but the fixed build had not yet been re-launched to the
  title screen at the time of writing.
* Reaching the title screen on that host also depends on a very old GPU
  (GeForce GT 730, NVIDIA driver 475.14) versus Minecraft 26.3's SDL3/OpenGL renderer. That is a
  hardware/driver question outside the launcher; the launcher now reports such crashes with the
  decoded native exit code instead of a bare number.

## 6. Pre-existing issues found, documented, deliberately not changed

1. `tsc -p tsconfig.json` (renderer) reports pre-existing type errors in `VictusCloudContext.tsx`,
   `WebControlPanelModal.tsx`, `ServersView.tsx`, `SettingsView.tsx` and `wallpapers.ts`. They do
   not fail `npm run build` (Vite/esbuild strips types without typechecking). The Electron main
   process typechecks cleanly. Out of scope for this release.
2. `electron/preload.ts` exposes `instances-export`, `instances-import-zip` and
   `modrinth-get-project`, but `electron/main.ts` registers no handlers for them.
3. The lightweight WPF installer patches `resources/app.asar` on an existing install and, on a
   machine with no prior install, downloads `…/releases/latest/download/VictusClient-Setup.exe`
   (itself). A true fresh-machine install must use the electron-builder NSIS installers.
4. `AutoUpdaterManager` falls back to *any* non-blockmap `.exe` release asset when
   `VictusClient-Setup.exe` is absent, which could select a full installer instead of the
   lightweight one.
